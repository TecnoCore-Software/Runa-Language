# DECISIONS.md — Provisional implementation choices

(v0.8 — the loop system. Entries #47–#68 cover the Class/Object spec,
#69–#75 cover the Loop System spec; earlier entries cover variables,
arithmetic, control flow and functions.)

Per the baseline spec (section 22), **the language designer decides Runa's
syntax**. To make the toolchain runnable, a few small implementation choices
had to be made. None of them are final. Each one is listed here so you can
✔ approve, ✘ veto, or change it.

| # | Provisional choice | Why it was needed | Status |
|---|--------------------|-------------------|--------|
| 1 | **Statements are newline-terminated.** The lexer emits `Newline` tokens; the parser expects a statement per line, allows blank lines. | A program longer than one line needs a separator rule. | ⏳ awaiting you |
| 2 | **Empty programs are valid** (compile to a lone `Halt`). | Sensible default; trivially changeable. | ⏳ awaiting you |
| 3 | **String literals:** double quotes only, no escape sequences, no multi-line strings (a newline inside a string is an error). | Escapes/multi-line strings are unspecified — so they are errors, not silently invented. | ⏳ awaiting you |
| 4 | **Keywords:** `true` and `false` are reserved words (cannot be identifiers). `printr` is NOT a keyword — it is an ordinary identifier recognized as a call. No comments yet (`#`, `//`, ... are lexical errors). | Booleans needed literal tokens; `printr` stays extensible for user-defined functions later. | ⏳ awaiting you |
| 5 | **ASCII-only identifiers for now.** Bytes ≥ 0x80 are `unexpected character` errors. | Unicode identifier policy is explicitly undecided in the spec. | ⏳ awaiting you |
| 6 | **Column numbers are byte-based** (ASCII assumption). | Simple and exact for ASCII; needs revisiting with Unicode. | ⏳ awaiting you |
| 7 | **Bytecode container v1** (magic `RUNA`, little-endian, typed constants/names/code). v1 replaced v0 when constants became typed; v0 files are rejected with a clear message. | The spec says version the format as the instruction set grows. | ⏳ awaiting you |
| 8 | **Instruction set v1:** `LoadConst`, `LoadGlobal`, `StoreGlobal`, `Call <name> <argc>`, `Halt`. | Exactly what confirmed syntax needs (`LoadGlobal`/`Call` added for variable reads and `printr`). | ⏳ awaiting you |
| 9 | **Reassignment is allowed** and variables are **dynamically typed** (`x = "a"` then `x = 99` is legal; last value wins). | Assignment accepts any expression; a type-discipline decision is still open. | ⏳ awaiting you |
| 10 | **Runtime error reporting has no source location yet** (bytecode carries no debug info — that's a later phase per the spec). | Debug info was explicitly postponed by the spec. | ⏳ awaiting you |
| 11 | **Three executables:** `runac` + `runavm` (the required split) plus a thin `runa` one-shot wrapper that calls the same separate components internally. | Convenient testing; spec explicitly permits a combined CLI. | ⏳ awaiting you |
| 12 | **`--dump-*` / `--trace` flags are tool diagnostics**, not language syntax. They expose each layer for testing (spec section 20). | Observable pipeline = testable pipeline. | ⏳ awaiting you |
| 13 | **Number literals:** decimal digit runs only — no signs, no decimal point, no separators. Stored as 64-bit signed integers; out-of-range is a lexical error. | `printr(123)` confirmed integer literals; negatives/floats would need unary minus / float syntax — not defined yet, so not invented. | ⏳ awaiting you |
| 14 | **Assignment RHS is any expression** (string, number, boolean, variable). | Same expression machinery as `printr` arguments; string-only RHS would be an artificial restriction. | ⏳ awaiting you |
| 15 | **Calls are resolved at compile time** against the stdlib registry: unknown callee or bad argument count = CompileError. The VM re-validates at runtime (defense in depth). | Typos should fail before running, not during. | ⏳ awaiting you |
| 16 | **`printr` output format:** arguments joined by single spaces + newline; strings print raw (no quotes). | Matches the designer's confirmed example `printr("Hello", name)` → `Hello Runa`. | ✅ designer-confirmed behavior |
| 17 | **Built-ins currently return no value** (nothing is pushed back onto the VM stack). | Return-value semantics are a designer decision; the Call design extends naturally. | ⏳ awaiting you |
| 18 | **Reading an undefined variable is a runtime error** (`undefined variable 'x'`). Compile-time detection needs declaration analysis — not built yet. | Compile-time undefined detection would wrongly reject conditional assignment patterns later; runtime check is the safe default for now. | ⏳ awaiting you |
| 19 | **The stdlib registry is static** (name + arity spec + native handler). No install step, no init order. | Compiler and VM must always agree on what exists; static = zero pitfalls. | ⏳ awaiting you |
| 20 | **Operator precedence:** `*` `/` `%` bind tighter than `+` `-` (designer-confirmed); operators of the same level are **left-associative** (`10 - 4 - 3` = 3, `100 / 10 / 2` = 5). | The designer's spec fixed the two tiers; associativity within a tier is the standard choice. | ⏳ awaiting you |
| 21 | **Arithmetic is integer-only** (64-bit signed, matching number literals): `/` truncates toward zero, `%` is the remainder with the sign of the dividend (C/C++ semantics). `10 / 3` = 3, `10 % 3` = 1. | Matches the designer's confirmed expected outputs; floats would be a separate designer decision. | ⏳ awaiting you |
| 22 | **Division/modulo by zero and signed 64-bit overflow are structured runtime errors** (`division by zero`, `integer overflow in '+'`), never crashes or silent wraparound. The VM contains zero undefined behavior. | A VM must define every outcome; erroring is the safe, debuggable choice. | ⏳ awaiting you |
| 23 | **Unary minus is NOT supported yet** (`-5`, `+5` in expression position = SyntaxError with an explicit "not supported yet" message). Subtraction can still produce negative results (`3 - 10` = -7). | Negative literals need a designer decision (unary operator? negative literal syntax?). Not invented. | ⏳ awaiting you |
| 24 | **`+` does not concatenate strings.** Arithmetic operands must be numbers; anything else is a runtime error (`unsupported operand types for '+': string and number`) with no implicit conversions. | String concatenation semantics (operator overloading? separate function?) is a designer decision. | ⏳ awaiting you |
| 25 | **Parenthesized grouping `( expression )` is supported** anywhere an expression is expected. | Explicitly required by the designer's spec. | ✅ designer-confirmed behavior |
| 26 | **Assignment RHS and call arguments accept full expressions** (`b = a * 2 + 1`, `printr("sum:", 2 + 2)`). | Same expression machinery everywhere; restricting to literals would be artificial. | ⏳ awaiting you |
| 27 | **`if` uses square brackets `[` `]` for its block** (`if <condition> [ ... ]`), statements inside are newline-terminated, blocks nest. `{}` is NOT used for control flow and stays reserved for future set/collection syntax. | Exactly as the designer's if-spec prescribed (designer-confirmed). | ✅ designer-confirmed behavior |
| 28 | **Comparison operators exist only in `if` conditions** in this version (`condition := expr (compOp expr)?` — one comparison, both sides full arithmetic expressions). Chained comparisons (`a < b < c`) are a syntax error, and comparisons in assignment RHS / call arguments are not part of the grammar yet (`a > 5` as an assignment value is a syntax error). | The if-spec asks for comparison conditions only; extending where comparisons may appear is a designer decision. | ⏳ awaiting you |
| 29 | **`==` and `!=` work on any two values; different kinds are simply unequal** (`5 == "5"` is false, not an error). No implicit conversions anywhere. | Equality semantics across kinds is the least surprising default; no conversions matches the strict arithmetic rule (#24). | ⏳ awaiting you |
| 30 | **Ordering comparisons (`>` `<` `>=` `<=`) work on numbers only.** Non-number operands are a runtime error (`unsupported operand types for '>': string and number`). | Same discipline as arithmetic (#22/#24); string/boolean ordering is undefined by the designer. | ⏳ awaiting you |
| 31 | **The `if` condition must produce a boolean at runtime** (`if 5 [ ... ]` = RuntimeError "if condition must be a boolean, got number"). Empty blocks (`if x == 1 [ ]`) and a one-line form (`if a == 5 [ printr("x") ]`) are accepted. | A strict-typed condition avoids silently defining truthiness; the block variants fall out of the block grammar naturally. | ⏳ awaiting you |
| 32 | **`elif` / `else` extend the `if` chain and must DIRECTLY follow the closing `]`** on the same line (`] elif ... [` / `] else [...`). An `elif`/`else` after a newline is a clean syntax error, not a continuing branch. | The designer's spec shows the chain inline; keeping it inline makes the chain unambiguous with the newline-terminated statement grammar (#1). | ⏳ awaiting you |
| 33 | **Chain discipline (parser-enforced):** at most ONE branch of a chain executes; `else` is optional, must be the final branch, and cannot repeat; `elif` may repeat any number of times but never after `else`. Standalone `elif`/`else`, `elif` after `else`, and duplicate `else` all produce specific SyntaxErrors with exact locations. | Exactly the designer's elif/else spec (sections 4–5); specific messages beat generic "expected a statement" noise. | ⏳ awaiting you |
| 34 | **New bytecode instruction: `Jump <u32>`** (unconditional), appended AFTER `JumpIfFalse` so every existing opcode number stays stable. Container stays v1 — old `.rbc` files remain loadable. A taken branch emits `Jump` to the chain end so the remaining branches are skipped. | elif/else needs an unconditional skip; the append-only pattern preserves backward compatibility (same approach as Eq..Le). | ⏳ awaiting you |
| 35 | **`fun` and `return` are reserved words** (TokenType::Fun/Return). `fun name(a, b) [ ... ]` declares; `return` / `return expr` exits. `( ) ,` tokens were reused (no redefinition); the body uses the existing `[ ... ]` block syntax — `{}` stays reserved. | Exactly the function-system spec; existing block machinery is reused unchanged. | ⏳ awaiting you |
| 36 | **Function model is exactly the requested scope:** per-invocation independent local scope, parameters bound by value before the body runs, assignments inside functions always create/update locals, locals die with the invocation. NO closures / lexical capture / lambda / nested functions / global mutation from inside functions / static or thread-local variables. | The spec's section-7 list; everything beyond it stays a future decision. | ⏳ awaiting you |
| 37 | **Reads inside functions check locals first, then globals** (new `LoadVar <u32>` opcode). Reading a global from a function is allowed; assigning never touches globals (`StoreLocal <u32>`, a same-named global is shadowed). At the top level, LoadGlobal/StoreGlobal behave exactly as before. | Mutation of globals is explicitly excluded by the spec, but the spec is silent about reads; locals-first-then-globals is the least surprising resolution. | ⏳ awaiting you |
| 38 | **`none` is a new runtime value kind** (distinct from string/number/boolean). Bare `return` and reaching the end of a function body produce it; `printr` renders it as `none`; `none == none` is true, `none == 0 / false / ""` are false; arithmetic on it is a normal type error. | The spec requires a "no value" runtime value that must not be confusable with false/0/""; a distinct kind is the cleanest guarantee. | ⏳ awaiting you |
| 39 | **Calls are expressions everywhere** (new AST FunctionCallExpr; a bare call statement is an ExpressionStatement whose value the compiler discards with a new `Pop` opcode). **Built-ins now return exactly one value** (`printr` returns `none`) so every call — user or builtin — leaves exactly one value on the stack. | The spec demands calls be usable in assignments/arithmetic; uniform call semantics prevent stack imbalance by construction. This supersedes decision #17. | ⏳ awaiting you |
| 40 | **Function names are reserved and checked at compile time:** duplicate function names, a function named like a built-in, assigning to a function name (before or after its declaration), and using a function name as a value are all CompileErrors. Functions and variables remain separate namespaces. | The spec's section 20/17/18 requirements; controlled name collisions beat confusing runtime behavior. Function-as-value stays unimplemented by spec. | ⏳ awaiting you |
| 41 | **Declaration order:** the compiler collects ALL top-level function declarations first (pass 1), then compiles main code (pass 2), then function bodies after `Halt` (pass 3). Calls may appear before or after their declaration in the file; a function definition emits no main-path code. | The spec's section 21; the whole program is compiled before execution, so hoisting the registry is free and deterministic. | ⏳ awaiting you |
| 42 | **Bytecode container v2:** a `functions` table (name, parameter names, u32 entry offset) sits between the names pool and the code. Layout changed ⇒ version bumped; v0/v1 files are rejected with a clear message. Function opcodes appended after `Jump` so all older opcode numbers stay stable: `ReturnValue`, `ReturnNone`, `Pop`, `LoadVar <u32>`, `StoreLocal <u32>`. `Call` is unified (user functions first, then built-ins). | The spec's section 22; versioning discipline mirrors the v0→v1 transition. Supersedes the container part of decision #34's note. | ⏳ awaiting you |
| 43 | **The VM owns call frames:** each `Call` pushes a frame {return address, operand-stack floor, function name, independent locals map with parameters bound}; `ReturnValue`/`ReturnNone` unwind it and hand one value to the caller. No global mutable state tracks locals; recursion works because frames never share anything. | The spec's sections 14–15; frame-per-invocation is the minimal structure that makes recursion and independent locals automatic. | ⏳ awaiting you |
| 44 | **Call stack depth is limited to 10000 frames** (provisional). Deeper recursion fails with `call stack overflow while calling 'f' (maximum call depth of 10000 exceeded)` — a clean RuntimeError, never a crash. | The spec requires a call-stack-overflow error; a fixed limit turns runaway recursion into a diagnosable event. The number is a designer-adjustable default. | ⏳ awaiting you |
| 45 | **Nested function declarations and top-level `return` are COMPILE errors** (specific messages). The parser accepts both forms anywhere so the error kind matches the spec; the compiler's context flags (inFunction / top-level walk) produce the diagnostics. | The spec's sections 26/28 explicitly prescribe CompileError for these. | ⏳ awaiting you |
| 46 | **Malformed function bytecode is rejected twice:** the deserializer validates duplicate function/parameter names and entry offsets within code bounds; the VM re-checks registry duplicates, entry offsets, frame stack balance on return (`stack imbalance on return from 'f'`) and return-without-frame. All RuntimeErrors, never crashes. | The spec's section 27; hand-crafted or corrupted files must fail loudly. | ⏳ awaiting you |

## Hard rules respected (spec section "Hard Rules")

- ✅ No syntax beyond designer-confirmed forms was assumed or invented
  (`printr`, arithmetic, `if`, and the complete function system were
  specified by the designer, then implemented verbatim).
- ✅ Compiler and VM remain separate components (and separate executables).
- ✅ The `.ru` extension and the assignment syntax are unchanged.
- ✅ The VM never parses `.ru` files; the compiler never executes programs.
- ✅ Every layer is tested before being relied upon by the next one (473 tests).

| 47 | **Class-system container is v3**: a `classes` table (name, parent index, flags, interfaces, fields with initializer offsets, methods with entries) joins the layout; a `null` constant kind was added. v0/1/2 files are rejected — recompile. All pre-existing opcode numbers stayed stable (class opcodes appended after `StoreLocal`). | The spec adds classes; the container is versioned by layout (established rule). | ⏳ awaiting you |
| 48 | **Class declaration syntax is exactly as specified**: `class (Name) [ ... ]`, `class (Child : Parent) [ ... ]`, `interface (Name) [ ... ]`, `abstract class` / `abstract fun`, `class (X) implements A, B`. `:` and `.` and `===` became tokens; 14 new reserved words (`class interface new self super constructor static public private abstract implements override null is`). | Designer's 30-section spec; nothing invented beyond it. | ✅ designer-specified |
| 49 | **Fields require a default value** (`name = "pride"`); the default expression is evaluated per `new` in base→child class order, then the constructor runs. Field initializers may not use `self`/`super`/`return` (fields are built before the object is usable). | The spec always shows initialized fields; evaluation order must be deterministic. | ⏳ awaiting you |
| 50 | **Construction plan**: `new` runs field-initializer blocks base→child, then the (single, non-inherited) constructor. Constructors cannot `return <value>` (bare `return` exits early). A class without a constructor takes `new X()` with zero arguments. | Spec sections 2/6; deterministic single-pass initialization. | ⏳ awaiting you |
| 51 | **`self`** is available only in instance methods and constructors; it is a value (`printr(self)` → `Car#1`), never an implicit argument, and cannot be assigned. Static methods and static initializers that use `self` are CompileErrors. | Spec section 5. | ⏳ awaiting you |
| 52 | **Object display format**: `printr(self)` / object dumps show `ClassName#<serial>` (e.g. `Car#3`), with a per-run serial starting at 1. `--dump-globals` shows the same. | The spec requires objects to become runtime values; a deterministic, non-address format keeps tests stable. | ⏳ awaiting you |
| 53 | **Overload resolution is by exact argument count**, walking from the receiver's runtime class up the parent chain (nearest match wins). Two methods with the same name+arity in one class are a CompileError; mixing static and instance overloads of one name is a CompileError. Dynamic receivers resolve at RUNTIME (Runa has no static types); `self.`/`ClassName.` calls are compile-checked. | Spec section 22; arity is the only differentiator Runa has. | ⏳ awaiting you |
| 54 | **Visibility**: `private` members are accessible only from the DECLARING class itself (other instances of the same class included — Java-like); derived classes do NOT see parent privates; everything unmarked is public. Illegal access is a CompileError for statically-known sites (`self.x`, `X.y`) and a RuntimeError through dynamic receivers (`obj.x`). | Spec section 9 chose public/private without defining the boundary. | ⏳ awaiting you |
| 55 | **Static members** live in per-class storage: static fields initialize once at program start in class declaration order; inherited statics resolve to the DECLARING class's storage (`Car.count` reads Vehicle's slot when Vehicle declares it). Static methods cannot use `self`/`super` and cannot be called through instances (`car.static()` is an error). | Spec sections 10/11. | ⏳ awaiting you |
| 56 | **Override discipline**: a concrete method matching a visible CONCRETE parent method must be marked `override`; implementing an abstract parent method with a plain `fun` is allowed (that is the implementation). `override` must match a visible parent method (name + arity). `static`/`private`/`abstract` methods cannot be marked or used as override targets. | Spec section 14; the marker catches accidental shadowing. | ⏳ awaiting you |
| 57 | **Abstract enforcement**: `abstract class` cannot be instantiated and cannot have a constructor; `abstract fun` has no body and only exists in abstract classes; a CONCRETE subclass must implement every inherited abstract method and every interface contract (checked at compile time; abstract classes may defer). | Spec section 16. | ⏳ awaiting you |
| 58 | **Interfaces** declare methods without bodies (no fields, no constructor, no modifiers, no nesting, no inheritance between interfaces). `implements` is validated at compile time; satisfaction may come from anywhere in the parent chain. `x is Interface` is true for implementing classes. | Spec section 17, minimal reading. | ⏳ awaiting you |
| 59 | **`==`/`!=` on objects is STRUCTURAL equality**: two objects are equal iff they share the same runtime class and every instance field compares equal (recursively, depth-limited to 64 — cyclic field chains produce a clean runtime error). Different classes simply compare unequal; object vs null/non-object is false. | Spec section 18 asked for defined, deterministic semantics; there is no user-definable equality method in this version. `===` covers identity. | ⏳ awaiting you |
| 60 | **`===` is reference identity** for objects (same instance); `null === null` is true; non-object pairs behave like `==`; object vs non-object is false. `!==` is NOT part of the language (not specified) — use `===` in an `if/else`. | Spec section 19. | ⏳ awaiting you |
| 61 | **`null`** is a value of its own kind (typeName `null`, prints `null`), distinct from `none`. Member access or method calls on null produce `null dereference ...` RuntimeErrors. `null is X` is always false. | Spec section 20. | ⏳ awaiting you |
| 62 | **Nested classes** are declared with the same syntax inside a class body; they are registered under a qualified internal name (`Car::Engine`) and visible ONLY inside the direct enclosing class body (shadowing outer names is allowed). Interfaces cannot be nested. | Spec section 21, "implement only as much as needed". | ⏳ awaiting you |
| 63 | **`is` lives in conditions** (`if x is Car [ ... ]`), like the existing comparison operators. It matches the runtime class, any ancestor, or any implemented interface. | Spec section 24; consistent with comparisons-only-in-conditions. | ⏳ awaiting you |
| 64 | **Class names are reserved identifiers**: assigning to one, reading one as a value, calling one as a function, or defining a function/builtin with a top-level class name are CompileErrors. Instantiate with `new`, access statics via `ClassName.member`. | Spec section 26 (classes are compile-time entities; no class-values, consistent with no function-values). | ⏳ awaiting you |
| 65 | **Method/constructor frames carry self + owner class**: virtual dispatch starts at the receiver's runtime class; `InvokeSuper` starts at the parent of the class where the CURRENT method was declared and keeps the same self. Private checks compare the declaring class against the frame's owner. | Spec sections 13/15/25. | ⏳ awaiting you |
| 66 | **Lifetime is reference counting** (`std::shared_ptr`): assignment/argument passing share the reference; memory is reclaimed when the last reference disappears. No `delete`/`free`/destructor syntax exists, per the spec. Recursive construction (`class (A) [ x = new A() ]`) is bounded by the call-depth limit → clean RuntimeError. | Spec section 23; the simplest model compatible with the current VM. | ⏳ awaiting you |
| 67 | **Malformed class bytecode is rejected twice**: the deserializer validates parent indices and initializer/method entry offsets; the VM re-validates class indices, interface names, inheritance cycles, constructor arity, frame stack balance (including plan frames) and plans out of order. All RuntimeErrors, never crashes. | Spec section 25; hand-crafted or corrupted files must fail loudly. | ⏳ awaiting you |
| 68 | **Misplaced declarations**: class/interface declarations are valid only at the top level or directly inside a class body — inside functions or if-blocks they are CompileErrors. Interfaces cannot be nested or inherit. `constructor` cannot take modifiers. | Spec sections 1/21; keeps the declaration model simple. | ⏳ awaiting you |
| 69 | **Loop syntax is exactly as specified**: `loop <condition> [ ... ]` and `for i = <start> to <end> [ ... ]`, with `break`/`continue` as bare statements that take no value (`break 5` is a SyntaxError). 5 new reserved words (`loop for to break continue`); `while` is deliberately NOT a keyword. The `loop` condition uses the same grammar as an `if` condition (comparisons, `is`, calls); the `for` bounds use the general expression grammar. No `for ... in`, no step, no decrement, no range objects. | Designer's 16-section Loop spec + strict scope (section 14); nothing invented beyond it. | ✅ designer-specified |
| 70 | **`for` bounds are evaluated exactly ONCE at loop entry** and the end value is kept in a compiler-internal hidden slot (`#for_endN#`; `#` cannot appear in source identifiers so a collision is impossible, and these slots are filtered out of `--dump-globals`). The range is fixed at entry — side effects in the bounds happen once. | The spec leaves evaluation frequency undefined; a fixed range matches the simple, predictable counting-loop model (Pascal/Swift style) instead of C-style re-evaluation. | ⏳ awaiting you |
| 71 | **`start > end` runs ZERO iterations** — the bound `counter <= end` is checked before the first pass, so an inverted range is an empty range, never an infinite loop. After a completed loop the counter equals `end + 1`; after a zero-pass loop it keeps `start`. | The spec required a defined, documented, non-hanging behavior consistent with inclusive bounds. | ⏳ awaiting you |
| 72 | **The `for` counter is an ordinary variable** in the current scope: a local inside functions/methods/constructors (`StoreLocal`), a global at the top level (`StoreGlobal`). Assigning to it inside the body is legal ordinary assignment that affects the iteration; class/function names stay reserved as counter names. Recursion is safe because each invocation gets its own frame locals (counter and hidden slot included). | The spec defines no special counter scope; ordinary-variable semantics reuses the established v0.6 rules (#37) exactly. | ⏳ awaiting you |
| 73 | **Loops compile to plain `Jump`/`JumpIfFalse` — zero new opcodes and zero container change** (FORMAT_VERSION stays 3; existing v3 files stay valid). `loop` lowers to cond → JumpIfFalse(end) → body → Jump(cond); `for` adds the init block (start → counter, end → hidden slot), the `Le` inclusive bound check and the increment block `counter = counter + 1`. `continue` targets the condition (`loop`) or the increment (`for`); `break` targets the first instruction after the loop; every target uses the same backpatching style as if/elif/else. The VM does not know loops exist. | Spec section 8 asked for conditional + unconditional jumps; the existing opcode set already covers loops completely, so the append-only opcode policy is preserved trivially. | ⏳ awaiting you |
| 74 | **break/continue validation is a compiler loop-context stack**: every compiled loop pushes a context collecting its break/continue patch sites, so nested loops always patch the NEAREST loop; entering a function/method body clears the stack, so break/continue can never cross a function boundary — and outside any loop they are CompileErrors (`break outside of a loop`, `continue outside of a loop`). | Spec sections 3/4/5/6. | ⏳ awaiting you |
| 75 | **The `JumpIfFalse` condition message was generalized** from "if condition must be a boolean" to "condition must be a boolean, got N" — the same instruction also guards `loop` conditions and the `for` bound check now. Two pre-existing test needles were updated accordingly (syntax and behavior unchanged). | One instruction should carry one neutral message; a loop user seeing an `if`-specific error would be confused. | ⏳ awaiting you |

| 76 | **RPR is a real, versioned binary container** (magic `RPRF`, version 1, u32 flags reserved for future compression): header + dedicated manifest section + file table (path/offset/size per entry) + concatenated payloads. The reader validates magic, version, flags, path safety (no `..`, absolute paths, backslashes, empty segments, NULs), duplicates, bounds and overlaps, and reads archives fully FROM MEMORY — normal import never extracts anything. Extraction exists only for `rpr extract` (development) and for native binaries (see #82). | Spec sections 5/32/33 demanded a real format readable from memory with total validation; compression is deferred rather than faked. | ⏳ awaiting you |
| 77 | **`import` is whole-program static linking at compile time.** The compiler loads each `math.rpr` in memory, compiles its entry as its own unit and merges it into ONE chunk under hidden names (`#pkg.math#sqrt`, `#pkg.math#Vector`, package globals as `#pkg.math#uses`, init bodies as `#init#math#`). Zero new call opcodes — `math.sqrt(25)` compiles to the plain `Call` of a prefixed name, `new graphics.Window()` to a plain `NewObject` of a prefixed class. The library stays in its package on disk; nothing is copied into the user's source or AST (the units compile separately with separate scopes). | Spec sections 9/11/38: no source copy-paste, reference-style linking; the lowest-risk binding compatible with the existing Compiler/VM (spec section 11 explicitly delegates linking details). | ⏳ awaiting you |
| 78 | **Search paths and precedence**: `<project>/runalibs` (project = directory of the main source), then `<executable dir>/runalibs/internal`, then `<executable dir>/runalibs/external`. First match wins; the executable dir is resolved via /proc/self/exe (Linux), GetModuleFileNameW (Windows), _NSGetExecutablePath (macOS) — independent of the working directory. Package identity = manifest name, which must equal the import name AND the archive file name (mismatch = CompileError). Duplicate loads are deduplicated (diamond imports load once); re-importing the same package in one unit is idempotent; duplicate selective symbols are CompileErrors. | Spec section 12 required deterministic paths/precedence/errors; Python-style `import x` + `from x import y` coexistence felt natural for `import math` + `as "math" import {...}`. | ⏳ awaiting you |
| 79 | **Package exports are top-level functions and classes only.** Package top-level VARIABLES are internal state: hidden from `--dump-globals` (they start with `#`), invisible to importers, but readable from the package's own functions via a frame-prefix global fallback. Library top-level STATEMENTS run once at startup as a per-package init body, in dependency order (each unit's class statics, then its init body, then the next unit). | Spec section 6/37; exporting variables cross-unit would need const/mutability semantics the language does not have yet. | ⏳ awaiting you |
| 80 | **Selective import binds at compile time**: `as "math" import {sqrt, Vector}` maps the names to the package's prefixed symbols; every use site compiles to the same code as a namespace call. Unknown symbols, duplicate bindings and conflicts with unit-local functions/classes/builtins/other imports are CompileErrors with the symbol's location. | Spec section 10/37; compile-time binding keeps runtime zero-cost and errors early. | ⏳ awaiting you |
| 81 | **Import cycles are CompileErrors** (`import cycle detected involving package 'x'`), detected via an in-progress set during the dependency walk. Units compile in topological order (dependencies first, main last), which also fixes the startup order (#79) and the class-table ranges. | Spec section 12 (deterministic behavior); cycles have no defined meaning in a static-linking model. | ⏳ awaiting you |
| 82 | **`cimport` paths are package-relative and context-aware**: in the main unit they resolve against the project root on disk; inside a library they resolve INSIDE that package's RPR (package context). The binding name is the native manifest's `"name"`; calls go through `ns.func(...)`. A native package may NOT be pulled in by normal `import` (type `native` manifest + import = CompileError; hybrid packages load their natives only when their own init.ru cimports — enforced by a dedicated test with a garbage .so that `import` must ignore). | Spec sections 13/15/16/17/34/35: two pipelines that stay distinguishable, native loading strictly explicit. | ⏳ awaiting you |
